# ① 第一性原因溯源

引入点：PR #48 的数据修复脚本。

修复时我做的推理是：
1. 删掉 E2E 污染的成交/持仓
2. 现金按「初始 − 真实成交支出」重算
3. 曲线截断到污染发生之前（65 点）
4. cursor 回退到"截断处对应的推进位置"

第 4 步我写的是 `cut - 1`（= 64），而 `cut` = 65 是保留的点数。

**错误假设**：「曲线点数 = cursor + 1」（即 cursor 是 0-based 索引）。
**实际情况**：`cursor == 曲线点数`（cursor 是"已处理到的 bar 序号"，
第一次 `step()` 后 cursor 从 0 变 1，同时记下第 1 个曲线点）。

这个假设我当时**没有验证**，只是"看起来合理"。而原状态 `72/72`
恰好就在文件里摆着 —— 只要顺手看一眼两个数字是否相等就能发现。

# ③ 系统性漏洞

> **数据修复的验证标准不完整：只验「当下自洽」，没验「能否正确继续」。**

「当下自洽」只覆盖同一时点的字段间关系（现金↔成交、持仓↔成交）。
但账户是**有状态机**的：`cursor` 决定"下一步处理哪根 bar"，
它和「已记录的曲线」构成一对**跨时点**约束，只有推进时才校验。

这是一类结构性盲区，不是这次的偶发失误：
凡是"修复后还要继续用"的数据，都存在"当下对、继续错"的可能。

同族历史缺陷（呼应本项目既有主题）：都是「**看起来正常、结果会错**」——
- 空池假成功（返回 ok 但什么都没做）
- `.env` 配了不生效（打印"未配置"而非报错）
- 统计不落盘、start 抹历史

# ⑤ 预防措施

1. **数据修复的标准动作加一步「隔离演练」**（本次确立）：
   复制真实状态到临时目录 → 走生产同款构造路径 → 真推进一步 →
   校验「下一状态」而不只是「当前状态」。
2. **修复后必须先回答「下一步会发生什么」**，再宣布修完。
   凡是有游标/偏移/索引的修复，一律对照原状态验证不变量（原状态 72/72 就是现成的答案）。
3. **不变量测试要覆盖「跨时点关系」**，不能只覆盖「同一时点字段关系」。
4. 生产数据测试在 CI 必然 skip —— 这类约束必须**同时**有一份合成数据的等价测试，
   否则等于没有保护。
