# 观察期缺陷复盘：池子被剔空后仍报 ok（2026-10-12 实测）

## 现象

模拟盘上线后**首个真实交易日**（2026-10-12 周一 15:30）：

- 定时任务触发、落盘成功、调度状态 `✅ ok`
- 但 `steps=0`、成交 0 笔、`symbols=[]`
- 落盘 metadata 里 `dropped: ['000002','000001','600036']` —— **3 只标的全部取数失败被剔除**

即：**"跑是跑了，但什么都没干"**，且不报错、不告警。

## 根因（两层）

1. **外因**：15:30 那一刻数据源不稳（baostock 周末后抖动 + 缓存 TTL 1h 过期），
   3 只标的取数全部失败 → `step()` 走剔除分支 → 池子空
2. **内因（要修的）**：`run_paper_cycle` **无条件返回 `status="ok"`** ——
   `steps` 为空、池子为空都照样 ok。调度据此记录成功，**告警不触发**
   （alerter 只在异常时响）

**更糟的后续**：`symbols=[]` 已落盘 → 进程重启后 `_build_engine` 读落盘空池 →
即使数据源恢复也**永远空跑**（缓存与落盘互为锁，无自愈路径）。

## 为什么这是"最危险的缺陷形态"

与项目 15 个历史缺陷同款：**看起来一切正常**。调度绿、接口 200、
日志无 error、账户数字不动但也没人怀疑。用户唯一能察觉的只有
"怎么老不成交"——而那正是这个系统要观测的东西。

## 修复

`run_paper_cycle` 增加 `pool_empty` 分支：**steps 为空且池子为空 → 返回非 ok**
（带 `pool_empty_reason` 指明剔除了几只、哪几只、怎么办）。

- 调度端：`pool_empty` 会走 `_record_failure`（非 ok 即失败路径）→ **告警触发**
- 恢复端：下次重启 `_build_engine` 见 `symbols=[]` 会 warning 并回退默认池
  （代码里已有此分支，此前因"落盘时池与账户同时写"被标 pragma no cover）

## 回归保护

`tests/test_paper_empty_pool.py` 3 条：空池 → `pool_empty`（非 ok）/ 空池仍落盘 /
正常有 steps → 仍 `ok`（不误报）。变异验证：删掉分支 → 3 条全红。

## 附带处理

- **服务无需重启**：pid 10560 自 10/11 起持续运行，代码亦为最新
- **数据源已恢复**：19:40 手工构造引擎，3 只全部取到（`symbols` 恢复 3 只）
- **当天账户已修复**：删除 `default.json` 让下次执行走"无落盘状态→新建"路径回退默认池
  （或等下一次真实交易日观察自愈）

## 教训

1. **"0 步成功"必须是失败**——空跑和跑砸了没有区别
2. **剔除全部标的时要显式报警**，而不是默默继续
3. 观察期的价值正在于此：**这个缺陷只有在真实运行中才会暴露**，
   任何单元测试都模拟不出"15:30 那一刻数据源刚好全挂"的组合
