# 缺陷反思 2026-10-14：`.env` 配置静默失效（文档教了，代码没读）

> 按质量节拍 **Bug 反思循环 5 步 SOP（QM-5）** 执行：根因溯源 → 逃逸链 → 系统性漏洞 → 修复+回归保护 → 预防措施。
> 本轮是「**不报错，但结果是错的**」家族的又一变种：**用户按文档配好了，系统照旧说不配**。
> 激活它的，是每日兜底任务连续三天的正常执行——正是"看起来没问题"的假象。

## 摘要

| # | 发现 | 性质 | 严重度 | 暴露点 |
|---|------|------|--------|--------|
| A | `.env.example`/`OPERATIONS.md` 教用户把 `STOCK_PING_URL` 写进 `.env`，但没有任何代码把 `.env` 加载进 `os.environ` → 进程外脚本直读环境变量 → 配了也不生效，只打印"未配置" | 文档/代码行为矛盾 | 中（静默） | 每日兜底任务实跑 |
| B | 同一缺口影响 `FALLBACK_BASE_URL`（容器部署场景）——`.env.example` 没提，但代码注释提了 | 同源 | 低（未用） | 代码审查 |

**影响面修正（排查中收缩）**：`STOCK_API_TOKEN` / `STOCK_NOTIFY_*` **不受影响**——
它们走 pydantic-settings（`env_file=".env"` 自己会读）。缺口精确地落在
**进程外脚本**这一条路径上，这比初判的"整个项目都不加载 .env"窄得多。

---

# ① 第一性原因溯源

引入点：**commit `a94b487`（2026-10-10，"feat(ops): TD-10 死信开关"）**。

那次提交做了三件事：实现 `watchdog_ping.py` 的 ping、在兜底脚本里接线、
在 `.env.example` 写配置步骤。前两件对，第三件**埋了雷**——文档承诺了一条
代码从未实现的加载路径。

当时的意图无疑是"用户配 `.env` 就能用"。之所以写成这样，是因为**服务内
路径确实是这个效果**（pydantic-settings 读 `.env`），作者把服务内的经验
直接套到了进程外脚本上——两个路径的配置机制根本不同：

| 路径 | 读取方式 | `.env` 生效？ |
|------|---------|--------------|
| 服务内（`get_settings()`） | pydantic-settings `env_file=".env"` | ✅ 一直对 |
| 进程外（`python scripts/paper_daily_fallback.py`） | `os.environ.get(...)` | ❌ 从未生效 |

而 `python-dotenv` 其实**早就装着**（pydantic-settings 的硬依赖，1.2.2）——
不缺工具，缺的是一行调用。

## 为什么表现为"静默"

三个条件叠加，让这个 bug 连报错都不会有：

1. `os.environ.get("STOCK_PING_URL")` 取不到值时返回 `None`——与"用户没配"**完全同形**
2. 兜底脚本对"未配置"的设计是**静默跳过**（`watchdog_ping.py` 的既定原则：不打扰）
3. 没有任何测试测过"配置从哪来"——`test_watchdog_ping.py` 的 10 条全是 mock HTTP 行为，
   没有一条验证过 `.env` → `os.environ` 这条链

结果：用户按文档配了死信开关，兜底照样打印"未配置"，**监控服务也收不到 ping**
（TD-10 想覆盖的"机器关机无人知"盲区原样存在），而一切看起来都很正常。

# ② 测试逃逸链（按层级）

| 层级 | 有没有测 | 为什么逃了 |
|------|---------|
| 单元测试 | ❌ 无 | TD-10 的 10 条测试全部 mock 掉 `ping_quiet` 与 HTTP，只验证"配了会不会 ping"；**没有一条回答"配置从哪来"** |
| 集成测试 | ❌ 无 | 兜底不起真实服务（`experiments/` 层才做），`.env` 加载不在其视野 |
| 代码审查 | ❌ 漏 | 文档与代码分居两个文件（`.env.example` vs `paper_daily_fallback.py`），review 看 diff 时**不会同时打开这两个文件** |
| 实跑验证 | ⚠️ 做过但方向偏 | TD-10 报告写了"实测跳过路径"——但测的是"没配时不打扰"，**没测"配了生不生效"** |

**逃逸根因（一句话）**：测试测的是「ping 的行为」，没人测「配置的来源」——
于是"文档承诺的配置通道根本不存在"这件事，在每一层都看不见。

# ③ 系统性漏洞定位

- **文件**：`tests/test_paper_daily_fallback.py`（TD-10 的 4 条接线测试）
- **机制缺陷**：`TestPingWiring._run_main()` 用 `monkeypatch.setenv("STOCK_PING_URL", ...)`
  **直接注入环境变量**——这在测试 `main()` 的 ping 行为时是对的，但同时也
  **掩盖了真实调用链**：真实场景里用户不设环境变量，只写 `.env`。
  测试用的注入方式与用户的配置方式不同源，于是缺口被完美遮住。
- **分类**：**门禁缺失漏洞**——"文档声明的配置项必须真实可达"这类断言
  项目里从来没有过。（`test_docs_consistency.py` 校验文档与代码的一致性，
  但只覆盖 README/架构树/数字来源，**没有覆盖"文档教的配置步骤是否真能生效"**。）

# ④ 修复 + 回归保护测试

**修复**（`scripts/paper_daily_fallback.py`）：

- 新增 `load_dotenv_files()`：把仓库根目录 `.env` 加载进 `os.environ`
  - `override=False`：**真实环境变量优先**（调度器/Docker 注入必须赢，
    否则测试环境被仓库自带的 `.env` 污染）
  - `.env` 缺失/为空/格式损坏 → 静默降级不崩（misconfiguration ≠ 不处理，
    与 `extract_port` 的既定哲学一致）
  - `python-dotenv` 缺失时打印说明并跳过（不以"它一定在"为前提）
- `main()` 第一个语句调用它（在任何 `os.environ.get` 之前）
- 模块级 `BASE` 在 import 时求值、早于加载 → `main()` 内按当前环境重算，
  让 `.env` 里的 `FALLBACK_BASE_URL` 也生效（同源第二个静默点）

**回归保护**（`tests/test_dotenv_loading.py`，10 条，全离线）：

| 场景 | 用例 |
|------|------|
| 正常路径 | `.env` 有 `STOCK_PING_URL` → `main()` 真的 ping |
| 优先级 | 真实环境变量不被 `.env` 覆盖 |
| 边界 | `.env` 不存在 / 空文件 / 全注释 |
| 异常 | 格式损坏（非法行/无键/无值）不崩 |
| 接线 | `main()` 第三语句必须是加载（顺序锁，见下） |
| 同源第二点 | `.env` 的 `FALLBACK_BASE_URL` 生效 |

**变异验证 3/3 全红**（含一次假锁修正）：

- M1 移除 `main()` 里的加载调用 → 3 红 ✅
- M2 `override=False` → `True`（覆盖真实环境变量）→ 1 红 ✅
- M3 加载挪到读 `STOCK_PING_URL` 之后 → **初版锁只红 1 条** ⚠️

**M3 假锁修正（本项目第 N 次）**：初版顺序断言是
`load_call < env_read`（源码位置比较）——把加载挪到 `ping_url = ...` **下一行**
仍满足（215 < 216），锁了个寂寞。收紧为"剥掉注释/docstring 后，
`main()` 的第三个语句必须字面等于 `load_dotenv_files()`"——同变异复打，2 红 ✅。

**实测端到端**（本地）：临时 `.env` 写 `STOCK_PING_URL` → 实跑兜底脚本 →
输出从 `ℹ️ 未配置死信开关` 变为真的去 ping（400 因 URL 是临时的，属预期），
退出码不受影响；原 `.env` 已还原。
