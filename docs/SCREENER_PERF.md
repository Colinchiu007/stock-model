# 选股扫描性能：实测数据与优化方案

> 实测日期：2026-10-19（本机，A 股，baostock 数据源）

## 问题：点「开始扫描」要等很久

## 实测基线（优化前）

| 场景 | 耗时 |
|---|---|
| 3 只 | 0.5s |
| 5 只（前端默认） | 0.6s |
| 30 只 冷缓存 | **64.2s** |
| 30 只 热缓存（同一批再扫） | **5.0s** |

## 结论：慢在首次取数，不是计算

冷/热差 12.8 倍，全部来自"每只股票首次要从 baostock 拉 2.5 年日线"（约 2s/只）。

## 为什么不用并发提速

代码里串行是**故意的**，不是疏忽：

```python
# 串行而非并发: baostock 是全局单连接, 其 query_* 接口不线程安全,
# 并发查询会互相抢占响应导致 RuntimeError(实测复现)。
```

并发方案已被证伪过一次（会导致 RuntimeError），不再考虑。

## 三个优化

### 1. 启动后台预热（最有效）

服务启动后用 daemon 线程静默拉取前端默认股票池：

```python
_WARMUP_SYMBOLS = ("000001", "000002", "600036", "000651", "600519")
threading.Thread(target=_warmup_common_pool, name="warmup-pool", daemon=True).start()
```

约束：
- 后台线程，**不阻塞服务启动**
- 单只失败只记录、不中断（`warmup_symbols` 返回 `(ok, failed)`）
- 整体 try/except，任何异常只 warn

实测：重启后 5 只在 ~10 秒内全部填好缓存。

### 2. 缓存 TTL 分时段

统一 TTL 的问题：盘中刚拉的数据，到收盘后正好过期，于是"晚上跑定时 + 早上看盘"每次都撞冷缓存。

```python
MARKET_CLOSE_HOUR = 15
CACHE_TTL_INTRADAY = 3600      # 盘中 1 小时（尊重 base_ttl 配置）
CACHE_TTL_AFTER_CLOSE = 43200  # 收盘后 12 小时
```

盘中不给留太长：否则用户下午看到的还是早上的数据。

### 3. 扫描进度反馈

消除"60 秒黑屏只能盯着转圈"的困惑。

- 后端：`/api/screener/progress?request_id=xxx` 返回 `{done, total, finished}`
- `request_id` 由**前端生成**并在扫描请求里带上 —— 请求还在飞时前端就已经知道该轮询哪个 id（用响应里的 id 就晚了）
- 进度记录 TTL 300 秒，过期自动清理
- 进度回调抛异常不影响扫描结果

## 优化后实测

| 场景 | 耗时 |
|---|---|
| 5 只 冷缓存（刚清缓存） | 11.5s |
| 5 只 热缓存 | **0.5s** |
| 30 只 热缓存 | 5.0s |

## 注意事项

- 预热是**优化而非主路径**：预热失败不影响任何功能，只是下次扫描慢一点
- 进度端点查不到 id 返回 `finished=true` 而不是 404 —— 轮询端点的"查不到"是正常状态
- 串行约束**没有改变**：提速来自缓存，不来自并发

## 回归保护

`tests/test_screener_performance.py`（6 条）：
- TTL 分时段策略（收盘后拉长、盘中保持）
- 预热遇坏标的跳过不中断、空输入 noop
- 进度逐只上报（严格 `[1/3, 2/3, 3/3]`）
- 进度回调异常不影响扫描

变异验证 4/4 全部会红：
- TTL 策略失效 → 红
- 预热遇错抛出 → 红
- 进度只在最后报一次 → 红
- 进度回调异常上抛 → 红
